# 雜湊表（hash table）理論基礎

## 雜湊表

首先什麼是雜湊表，雜湊表（英文名稱為 Hash table，也有一些演算法書籍翻譯為散列表，大家看到這兩個名稱知道都是指 hash table 就可以了）。

> 雜湊表是根據關鍵碼（key code）的值（value）而直接進行存取的資料結構（data structure）。

這麼官方的解釋可能有點懵，其實直白來講，陣列（array）就是一張雜湊表。

雜湊表中的關鍵碼就是陣列的索引（index）下標（subscript），然後透過下標直接存取陣列中的元素（element），如下圖所示：

![雜湊表1](https://file1.kamacoder.com/i/algo/20210104234805168.png)

那麼雜湊表能解決什麼問題呢？**一般雜湊表都是用來快速判斷一個元素是否出現在集合（set）裡。**

例如要查詢一個名字是否在這所學校裡。

要列舉（enumeration）的話時間複雜性（time complexity）是 O(n)，但如果使用雜湊表的話，只需要 O(1) 就可以做到。

我們只需要初始化（initialization）把這所學校裡學生的名字都存在雜湊表裡，在查詢的時候透過索引直接就可以知道這位同學在這所學校裡與否了。

將學生姓名映射（map / mapping）到雜湊表上就涉及到了**hash function，也就是雜湊函數（hash function）**。

## 雜湊函數

雜湊函數，把學生的姓名直接映射為雜湊表上的索引，然後就可以透過查詢索引下標快速知道這位同學是否在這所學校裡了。

雜湊函數如下圖所示，透過 hashCode 把名字轉化為數值，一般 hashCode 是透過特定編碼（encoding）方式，可以將其他資料格式轉化為不同的數值，這樣就把學生名字映射為雜湊表上的索引數字了。

![雜湊表2](https://file1.kamacoder.com/i/algo/2021010423484818.png)

如果 hashCode 得到的數值大於雜湊表的大小了，也就是大於 tableSize 了，怎麼辦呢？

此時為了保證映射出來的索引數值都落在雜湊表上，我們會再對數值做一個取模（modulo）的操作，這樣我們就保證了學生姓名一定可以映射到雜湊表上了。

此時問題又來了，雜湊表我們剛剛說過，就是一個陣列。

如果學生的數量大於雜湊表的大小怎麼辦？此時就算雜湊函數計算得再均勻，也避免不了會有幾位學生的名字同時映射到雜湊表同一個索引下標的位置。

接下來**散列碰撞（hash collision）**登場

### 散列碰撞

如圖所示，小李和小王都映射到了索引下標 1 的位置，**這一現象叫做散列碰撞**。

![雜湊表3](https://file1.kamacoder.com/i/algo/2021010423494884.png)

一般散列碰撞有兩種解決方法，鍊接（chaining）和線性探測法（linear probing）。

### 鍊接

剛剛小李和小王在索引 1 的位置發生了衝突，發生衝突的元素都被儲存在鏈接串列（linked list）中。這樣我們就可以透過索引找到小李和小王了

![雜湊表4](https://file1.kamacoder.com/i/algo/20210104235015226.png)

（資料規模是 dataSize，雜湊表的大小為 tableSize）

其實拉鏈法就是要選擇適當的雜湊表的大小，這樣既不會因為陣列空值而浪費大量記憶體（memory），也不會因為鏈接串列太長而在搜尋上浪費太多時間。

### 線性探測法

使用線性探測法，一定要保證 tableSize 大於 dataSize。我們需要依靠雜湊表中的空位來解決碰撞問題。

例如衝突的位置放了小李，那麼就向下找一個空位放置小王的資訊。所以要求 tableSize 一定要大於 dataSize，要不然雜湊表上就沒有空置的位置來存放衝突的資料了。如圖所示：

![雜湊表5](https://file1.kamacoder.com/i/algo/20210104235109950.png)

其實關於散列碰撞還有非常多的細節，感興趣的同學可以再好好研究一下，這裡我就不再贅述了。

## 常見的三種雜湊（hash）結構

當我們想使用雜湊法來解決問題的時候，我們一般會選擇如下三種資料結構。

* 陣列
* set（集合）
* map（映射）

這裡陣列就沒什麼好說的了，我們來看一下 set。

在 C++ 中，set 和 map 分別提供以下三種資料結構，其底層實作以及優劣如下表所示：

| 集合 | 底層實作 | 是否有序（ordered） | 數值是否可以重複（duplicate） | 能否更改數值 | 查詢效率 | 新增與刪除效率 |
| --- | --- | ---- | --- | --- | --- | --- |
| std::set | 紅-黑樹（red-black tree） | 有序 | 否 | 否 | O(log n) | O(log n) |
| std::multiset | 紅-黑樹 | 有序 | 是 | 否 | O(logn) | O(logn) |
| std::unordered_set | 雜湊表 | 無序的（unordered） | 否 | 否 | O(1) | O(1) |

std::unordered_set 底層實作為雜湊表，std::set 和 std::multiset 的底層實作是紅-黑樹，紅-黑樹是一種平衡二元搜尋樹（balanced binary search tree），所以 key 值是有序的，但 key 不可以修改，改動 key 值會導致整棵樹（tree）的錯亂，所以只能刪除（delete）和新增。

| 映射 | 底層實作 | 是否有序 | 數值是否可以重複 | 能否更改數值 | 查詢效率 | 新增與刪除效率 |
| --- | --- | --- | --- | --- | --- | --- |
| std::map | 紅-黑樹 | key 有序 | key 不可重複 | key 不可修改 | O(logn) | O(logn) |
| std::multimap | 紅-黑樹 | key 有序 | key 可重複 | key 不可修改 | O(log n) | O(log n) |
| std::unordered_map | 雜湊表 | key 無序 | key 不可重複 | key 不可修改 | O(1) | O(1) |


std::unordered_map 底層實作為雜湊表，std::map 和 std::multimap 的底層實作是紅-黑樹。同理，std::map 和 std::multimap 的 key 也是有序的（這個問題也經常作為面試題，考察對語言容器（container）底層的理解）。

當我們要使用集合來解決雜湊問題的時候，優先使用 unordered_set，因為它的查詢和新增與刪除效率是最優的，如果需要集合是有序的，那麼就用 set，如果要求不僅有序還要有重複資料的話，那麼就用 multiset。

那麼再來看一下 map，map 是一個 key value 的資料結構，map 中，對 key 是有限制，對 value 是沒有限制的，因為 key 的儲存方式是使用紅-黑樹實作的。

其他語言例如：Java 裡的 HashMap、TreeMap 都是一樣的原理。可以靈活貫通。

雖然 std::set 和 std::multiset 的底層實作基於紅-黑樹而非雜湊表，它們透過紅-黑樹來索引和儲存資料。不過給我們的使用方式，還是雜湊法的使用方式，即依靠鍵（key）來存取值。所以使用這些資料結構來解決映射問題的方法，我們依然稱之為雜湊法。std::map 也是一樣的道理。

這裡再說一下，一些 C++ 的經典書籍上，例如 STL 原始碼（source code）剖析，說到了 hash_set、hash_map，這個與 unordered_set、unordered_map 又有什麼關係呢？

實際上功能都是一樣的，但是 unordered_set 在 C++11 的時候被引入標準程式館（standard library）了，而 hash_set 並沒有，所以建議還是使用 unordered_set 比較好，這就好比一個是官方認證的，hash_set、hash_map 是 C++11 標準之前民間高手自發造的輪子。

## 總結

總結一下，**當我們遇到了要快速判斷一個元素是否出現在集合裡的時候，就要考慮雜湊法**。

但是雜湊法也是**犧牲了空間換取了時間**，因為我們要使用額外的陣列、set 或者是 map 來存放資料，才能實作快速的搜尋。

如果在做面試題目的時候遇到需要判斷一個元素是否出現過的場景也應該第一時間想到雜湊法！
